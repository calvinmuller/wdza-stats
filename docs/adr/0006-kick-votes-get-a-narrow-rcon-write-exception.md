# KickVote gets a narrow, explicit RCON write exception

[docs/adr/0003](./0003-gamification-notifications-stay-off-rcon-writes.md) kept RCON read-only for gamification Notifications, and explicitly said that if a write call was ever needed for some other reason, the read-only question should be asked again rather than assumed answered by that precedent. KickVote is that other reason: a crowd of players has no way to remove a disruptive player (typically a cheater) without one, and the game's own community expects a real vote-kick, not a dashboard flag someone might notice later. We now know, unlike at ADR 0003's time, that `POST /v1/players/{steamId}/kick` and `POST /v1/broadcast` both exist on the live RCON API, so the previous "we don't even know if a write endpoint exists" objection no longer holds. We're adding calls to exactly those two endpoints, only from the KickVote worker path, and nowhere else — every other admin/moderation action ADR 0003's `spec.md` deferred (ban, message, map/rotation control, config editing) stays out of scope and off RCON.

## Considered Options
- Keep RCON fully read-only and have a successful KickVote only flag the target for a Staff Member to kick by hand — rejected: defeats the point of a crowd-driven kick vote, which is to act immediately while the disruption is happening, not whenever a moderator next checks the admin panel.
- Require Staff Member authentication before any RCON write, i.e. only let a moderator/admin trigger the kick — rejected: ADR 0003's stated blocker was "no real authentication exists yet," and staff authentication now does exist ([docs/adr/0005](./0005-staff-login-replaces-the-secret-admin-url.md)), but gating the kick itself behind staff auth would just rebuild the "a moderator has to notice and act" system above under a different name. Real authentication existing doesn't mean this feature needs to depend on it: the crowd threshold, cooldown, and unconditional staff-cancel are the accepted substitute for authenticating each voter, since we still have no way to authenticate players at all — see `packages/db/src/kick-vote.ts`.
- Open up RCON writes generally now that two endpoints are confirmed to exist — rejected: no other feature has asked for one, and ADR 0003's boundary is worth keeping for everything it wasn't asked to cover.

## Consequences
- `apps/worker/src/rcon-client.ts` gains its first two write calls (`kickPlayer`, `broadcast`), which is a change to that module's stated invariant ("no write endpoint is exposed") — its comment needs updating alongside the implementation.
- The RCON credential remains full-access; nothing about this decision narrows what it *could* call, only what this codebase *chooses* to call. If a future feature wants a third write endpoint, ADR 0003's own advice still applies: ask explicitly, don't assume this ADR already opened the door.
- A KickVote's crowd threshold and staff-cancel are the only safeguards against a bad kick — there is still no per-voter authentication, so this trades "a moderator has to be watching" for "enough anonymous browser sessions have to agree," which is a materially different trust model worth remembering if kick-vote abuse ever shows up in practice.
